# 디자인 세션 (대상: $ARGUMENTS)

`AGENTS.md` §1 절차로 시작한다 (읽기 → 4줄 브리핑 → 사용자 확인). 추가로 대상 spec, `docs/erd.md`, `docs/ADR.md`, `docs/design/`(사용자가 그린 로파이)를 읽는다.

## 이 세션을 맡는 때
- 상태 `Draft`, 담당 `디자인` (초안 완성, 설계 대기). 코드가 아닌 설계 작업은 `Approved` 뒤에도 담당이 디자인이다.
- 끝낼 때: 상태 → `Designed`, 담당 → 사용자 (`Approved`는 사용자만).

## 역할 확인 (시작 시 첫 단계)
1. `SPEC.md`에서 `현재 단계 담당`이 **디자인**인 행을 찾는다. 인자가 있으면 그 행이 여기 해당하는지 확인한다.
2. 해당 행이 없거나 담당이 다른 세션이면 **작업하지 말고 멈춰서 알린다.** ("이 작업의 담당은 ○○입니다. `/○○`로 시작하세요.") 사용자가 지시하면 예외다.
3. 해당 행이 여러 개면 어느 것인지 사용자에게 묻는다.

## 역할
기획이 정한 "무엇"을 "어떤 구조로"로 바꾼다. UI는 사용자가 그린 로파이가 입력이다. AI는 UI를 새로 디자인하지 않는다.

## 하는 일
- 화면 → 화면이 필요로 하는 데이터 → API → ERD 순으로 도출한다. 필요한 엔티티만 `docs/erd.md`에 추가한다.
- spec의 '방식'을 쓴다: 허용 접근, 만들 파일 목록, 금지할 의존성·추상화.
- 선택지가 갈리면 **대안과 트레이드오프를 보여주고 사용자가 고르게 한다.** 결정은 사용자의 것이다.
- 갈린 결정은 ADR 후보로 정리하고 `docs/ADR.md`에 한 줄 추가한다. "결정과 이유"는 쓰지 않는다.
- 규모 추정부터 한다 (동아리원 수, 연습당 조회 수 등). 기술 선택은 그 뒤다.

## 기본적으로 하지 않는 일
- 구현 (→ `/dev`)
- 근거 없는 기술 선행 도입. 미리 정해두지 않는다.

## 종료
`/wrap`으로 마무리한다 (상태 전이는 위 '맡는 때'의 '끝낼 때'). `Approved`는 사용자만 바꾼다.
분량: 한 세션 = spec 하나의 설계.
