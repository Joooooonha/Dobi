# 보안 세션 (대상: $ARGUMENTS)

`AGENTS.md` §1 절차로 시작한다 (읽기 → 4줄 브리핑 → 사용자 확인).
**매일 여는 세션이 아니다.** 인증·인가 spec, 개인정보나 파일 업로드가 추가될 때, 첫 배포 직전에 연다.

## 이 세션을 맡는 때
- 사용자가 직접 호출했을 때. 인증·인가 spec, 개인정보·업로드 추가, 첫 배포 직전.
- 끝낼 때: 담당 칸을 이전 담당으로 되돌린다.

## 역할 확인 (시작 시 첫 단계)
1. 다른 세션과 달리 **사용자가 호출했다는 사실이 곧 담당 지정**이다. 담당 칸이 `보안`이 아니어도 진행한다.
2. 점검 대상 행이 불분명하면(`$ARGUMENTS`가 없거나 여러 개) 어느 것인지 사용자에게 묻는다.
3. 시작할 때 그 행의 담당 칸을 `보안`으로 바꾸고, 끝나면 이전 담당으로 되돌린다.

## 역할
공격자의 시점에서 읽는다. 읽기 위주이고, 수정은 `/dev`에서 한다.

## 점검 기준
**OWASP Top 10(최신 판)을 기준으로 한다.** 시작할 때 공식 목록(owasp.org/Top10)을 확인해 카테고리를 그대로 가져온다. 기억으로 목록을 쓰지 않는다. 백엔드 API이므로 **OWASP API Security Top 10**도 함께 본다.
- 이번 대상이 건드린 코드·설정에 해당하는 카테고리만 골라 점검한다. 해당 없는 카테고리는 "해당 없음(이유)"로 적는다.
- 아직 인증이 없는 단계에서는 해당 없음이 많다. 억지로 채우지 않는다.

**Top 10 밖이지만 이 프로젝트에서 반드시 보는 것**
- 개인정보: 이 레포는 공개다. 실제 동아리원 정보가 코드·시드·테스트·문서·로그에 있는지.
- 시크릿: 키·토큰이 커밋됐거나 이력에 남았는지, `.env` 취급.
- 배포 설정: 노출된 포트, CORS, 관리 화면, 에러 응답의 내부 정보 노출.

## 보고 형식
발견마다 `OWASP 카테고리 / 심각도 / 재현 방법 / 영향 / 권고`. 확인하지 못한 것은 "확인 못 함"으로 쓴다. 추측으로 심각도를 올리지 않는다.
발견은 spec 후보나 ADR 후보로 정리한다.

## 종료
`/wrap`으로 마무리한다. 끝나면 담당 칸을 이전 담당으로 되돌린다.
